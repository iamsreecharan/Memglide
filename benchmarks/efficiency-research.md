# Efficient context delivery: research and architecture choices

The observed retrieval cost regression cannot be fixed reliably by shrinking a source envelope alone. The next implementation should remove work that still occurs after source is delivered, retain exact passthrough for unsuitable tasks, and preserve the existing freshness and security checks. None of the mechanisms reviewed here guarantees token, latency or money savings.

The [JSON research ledger](efficiency-research.json) records sources, retrieval timestamps, full-response hashes, exact reading scopes, failed URLs and claim status. This review made **zero model requests**, changed no credentials or network policy, and supplies no new A/B result. Earlier reports remain unchanged.

## What the newer primary documentation changes

The current [OpenAI prompt-caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) is more specific than the earlier stable-prefix hypothesis. For GPT-5.6 and later, implicit caching places breakpoints at eligible message endings. The guide's “Extending a message can prevent reuse” example explains why keeping identical leading text inside a changed user message is insufficient: the old endpoint may no longer be a lookup boundary. Separate reusable messages or explicit supported content-block breakpoints can preserve that boundary.

Memglide's compact source prefix followed by a changing task is still **one native user message**. Canonical ordering and a smaller envelope are useful local properties, but they do not independently create a reusable source breakpoint. Earlier reports called this a hypothesis rather than a proven cache improvement; this review narrows the hypothesis further. It does not relabel their observations.

The same guide says GPT-5.6+ routing is automatic and `prompt_cache_key` is optional for separate accounting. Older-model cache-key advice should not be carried across model generations as a universal routing fix. The installed Codex source still computes an internal key/session header, but this does not reveal actual ChatGPT backend affinity, hit boundaries, cache retention or the cause of an individual miss.

The guide also documents that unchanged instructions, tools, schemas and conversation history matter to the rendered prefix. A task wrapper controls only a portion of that context. A session can preserve message history without guaranteeing a cache hit. The [conversation-state guide](https://developers.openai.com/api/docs/guides/conversation-state) says earlier input in a chained conversation remains billable; avoiding retransmission in an application is not the same as avoiding billed input.

## What native Codex can safely support

The installed native version is **0.159.2**, pinned to upstream commit [`ff6aec96948b70d94983af2641a6b67c94faeff5`](https://github.com/openai/codex/tree/ff6aec96948b70d94983af2641a6b67c94faeff5).

- The inspected [`exec` CLI definitions](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/exec/src/cli.rs#L1) accept a prompt string/stdin and optional images. [Root input construction](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/exec/src/lib.rs#L953) and [resume input construction](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/exec/src/lib.rs#L890) each add one text input. There is no arbitrary multiple-message or explicit-cache-breakpoint CLI option in the inspected surface. The [Responses request declaration](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/codex-api/src/common.rs#L279) does not carry the newer explicit cache options either. This is a scoped source inspection, not a claim about every future native/API feature.
- Supported explicit `codex exec resume SESSION_ID` uses the [native thread lifecycle](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/exec/src/lib.rs#L993). It can preserve actual earlier message boundaries for related work. Histories must remain independent between experiment arms, with complete sequence cost measured.
- Automatic source omission needs stronger evidence than an unchanged file hash and a thread ID. Native [compaction history construction](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/core/src/compact.rs#L649) can discard/truncate old user source. The inspected [JSONL event/item enums](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/exec/src/exec_events.rs#L9) expose no dedicated compaction event; the [item mapper](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/exec/src/event_processor_with_jsonl_output.rs#L149) drops unsupported variants. A receipt cannot prove full source is still in the model context after unobserved compaction.
- Sequence telemetry needs its own verification. [`usage_from_last_total`](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/exec/src/event_processor_with_jsonl_output.rs#L118) copies accumulated `ThreadTokenUsage.total` categories. The [protocol accumulator](https://github.com/openai/codex/blob/ff6aec96948b70d94983af2641a6b67c94faeff5/codex-rs/protocol/src/protocol.rs#L2275) adds last usage to totals and has reset/fill behavior. Before summing related-session results, establish whether resume restores those totals and validate final cumulative counts or category deltas. Blindly summing cumulative totals risks double counting; discontinuities require an unknown/incomplete result. Prior fresh-session comparisons do not have this particular multi-turn counting issue.

Keep manual `--context-supplied` available for a caller that actually knows the needed context is present. Do not use source hashes as a substitute for current source, policy, approval and retained-context validation. Do not promote untrusted source to developer/system instructions merely to manufacture a cache boundary.

## A small architecture with two context paths

The immediate priority is a conditional preparation path that costs no model calls, and an on-demand path for larger or ambiguous investigations. These are recommendations; implementation and validation results belong in the separately generated implementation/report artifacts.

1. **Keep the current cheap decline.** Off, caller-context supplied, missing focus or missing project should preserve the task bytes and avoid database/service/model work. An unknown need should leave native discovery available. The eight previous retrieval cases are too few to tune a universal byte threshold or semantic classifier.
2. **Give source delivery a task workflow when explicitly requested.** A small caller-provided validation recipe, or explicitly focused complete validation/config sources, may remove test-discovery steps that remain after source reads disappear. A declarative recipe should use bounded argv and a canonical relative working directory. Preparation must never execute commands, expand shell syntax, import repository code or infer an unsafe test command. Repository-derived recipes are advisory untrusted data; preserve provenance. Keep the existing full-source path when no recipe is supplied.
3. **Consolidate necessary context.** For larger tasks, a single bounded operation can return complete relevant implementations plus requested validation contracts, with explicit omissions and current source validation. Do not eagerly load an entire repository. When the cap cannot accommodate necessary full evidence, fall back honestly rather than silently cutting required bodies.
4. **Use native continuation deliberately.** Related tasks may reuse an existing native thread; unrelated work should not grow history indefinitely. No automated skip-on-receipt policy is justified until actual retained context/compaction state is available through a supported interface.
5. **Keep memory separate from current source.** Small provenance-bearing decisions and gotchas can help cross-session work, but source hashes do not prove old design decisions remain correct. Include memory creation, validation and readback in sequence costs. Default LLM extraction, embeddings, reflection workers and entity graphs add services/cost that the present ordinary-task evidence does not justify.

This follows the full main text of Anthropic's [effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) and [writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents). The former recommends lightweight identifiers, just-in-time loading and task-dependent hybrid retrieval, while acknowledging exploration latency. The latter recommends a few clearly distinct tools, consolidation of frequently chained work, concise high-signal outputs and realistic held-out evaluation. These are engineering principles, not independent Memglide gains.

The [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization) similarly prioritizes fewer requests and output tokens, while recommending classical computation when a model is unnecessary. Its numeric latency examples are heuristics, not expected Memglide speedups. [Cost guidance](https://developers.openai.com/api/docs/guides/cost-optimization) includes smaller models, Batch and Flex; those change quality, latency or execution settings and should not be used to claim an architectural improvement under matched native settings.

## How to establish that a change pays for itself

At the [previously verified Standard short-context prices](cost-pricing.json), one ordinary uncached input token costs the same as **20 cached-input tokens**, and one output token costs the same as **100 cached-input tokens**. Consequently, a small ordinary-input or output increase can outweigh a large reduction in cached input. A lower total-token count is not sufficient evidence of savings. Cache writes are a third, non-additive input category; native-reported zero has the documented upstream-omission caveat.

Use actual native usage, not a bytes-to-token conversion. Include every attempt, setup/preparation, retrieval/memory writes, local resources, failures and repeat runs. Keep actual billed dollars null unless attributable billing is obtained; list-price equivalence and hypothetical write sensitivity must remain estimates.

A workflow recipe is an additional B feature and must be declared as such. In a fair full-product comparison both arms receive the same ordinary task, start commit, environment, model and settings; B may obtain the advertised optional context from its explicit configuration. An **equal-recipe control/ablation** should also give A the same validation information to distinguish information advantage from retrieval/process improvement. Do not select a favorable pair or combine controls with active retrieval to claim that retrieval itself saves money.

Measure cost per independently successful task and whole-sequence cost for related work, alongside correctness, freshness, completeness, latency, sampled memory/CPU and native call telemetry where observable. Keep failed attempts and unknown fields. A fresh, frozen held-out benchmark is required after engineering checks; rerunning known development tasks is a probe, not independent validation.
