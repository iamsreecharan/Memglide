Memglide: Auditable, Bounded Repository Context for Coding Agents

SREE CHARAN REDDY KAILASAM
Repository context can reduce a coding agent’s search work, but selection, verification and added prompt text also have costs. Memglide
prepares bounded current-source context using lexical and static syntax evidence, abstains when selection is ambiguous, and optionally
supplies explicitly verified public commands and baseline counts. We evaluate its installed launcher against pass-through Codex
and source-only preloading on twelve custom feature tasks in newly pinned public repositories. A prospectively frozen balanced
design assigns three arms twice per task, producing 72 native workflows. All 72 pass finite feature, original public-check and integrity
requirements, with complete usage telemetry. The source-and-command workflow has 13.69% lower observed uniform token-tariff-
equivalent cost than pass-through and 10.04% lower cost than source alone. The exact conditional tests yield Holm-adjusted p=0.148 for
both contrasts; neither establishes a reduction under the prespecified rule. Mean workflow times are 40.56, 39.00 and 40.03 seconds for
pass-through, source-only and source-and-command modes. Source activates on seven tasks and abstains on five. The implementation
and evidence support a functioning, auditable context policy, while the small task-informed panel, finite checks and uncontrolled
caches limit claims about general savings or speed.

1   Introduction
Coding agents must find the source and test commands needed for a change. Providing that information in advance
may reduce their work, but preparation also costs time and adds to the prompt. The relevant question is whether the
complete workflow improves after selection, verification, prompt length, failed attempts and preservation of existing
behavior are counted. A compact source bundle or shorter serialized response cannot settle that question.
    Memglide is a local repository-context system with a native coding-agent launcher. The launcher uses lexical and
static syntax evidence to select current source, delivers complete selected files within fixed limits, and preserves the
original task when the evidence is insufficient. An optional workflow supplies public test commands and observed
baseline counts from an explicitly verified receipt. Preparation uses no auxiliary language model or embedding service.
The external coding model interprets the task, edits the code and runs checks.
    Earlier experiments revealed gaps between a working context system and an efficiency claim. Interactive MCP
retrieval could increase tokens and elapsed time. An automatic selector could abstain on most tasks, producing apparent
agent differences without evidence of a preload effect. A development-only compiler configuration could change a score
in a separate compatibility diagnostic. A provider failure could leave token usage unknown. These findings motivated a
comparison of the installed system with explicit records of activation, source protection, timing and missing data.
    Development included a 30-round search over prompt and verification approaches on three tasks, followed by a
two-arm comparison on eight new tasks. We treat that work as exploratory. The new study compares pass-through
Codex, source preloading, and source plus verified public-command context. Two repeats on twelve newly selected
public repositories yield 72 scheduled workflows. Private grading is deferred until native collection closes. The private
reference implementations, oracles and revealing plaintext logs are unavailable to the coding agent during collection.
    The tasks are author-designed feature additions to small public libraries. SWE-bench, by comparison, evaluates
patches for real GitHub issues [2]. Public task readiness informed a small production-file classification fix before

    We ask three questions. First, when does the installed policy deliver source and command context, and when

    The contributions are an implementation of bounded context preparation with verifiable receipts; an evaluation
method that separates activation, functional outcomes, timing and unavailable telemetry; and a development-to-
evaluation record that retains unsuccessful approaches. The study does not introduce new model weights, measure
memory-reuse benefits or establish a benchmark-leading coding agent.


2    Related work
Repository context has been studied as both a retrieval problem and part of code generation. RepoCoder combines a
similarity retriever with a pretrained code model in an iterative retrieval–generation pipeline [7]. RepoBench evaluates
retrieval, completion and a combined pipeline, including cross-file dependencies [4]. These settings separate the evidence
a retriever returns from the result of using it. Memglide evaluates functional patches with preserved public regressions
on small feature tasks, rather than code-completion similarity.
    Context length alone gives an incomplete account of useful input. Liu et al. varied the position of relevant information
in multi-document question answering and key–value retrieval. Performance often declined when relevant information
appeared in the middle of long contexts [3]. LLMLingua compresses prompts through a coarse-to-fine method with
token-level compression and model alignment [1]. Memglide uses lexical evidence and static syntax analysis to construct
bounded bundles of selected complete files. Preparation makes no auxiliary model call and can abstain when selection
or freshness checks fail. The present study includes no performance comparison with these approaches.
    Agent design provides a second point of reference. SWE-agent studies an agent–computer interface for automated
software engineering [6]. Agentless separates localization, repair and patch validation [5]. Memglide runs before
the installed coding agent, supplying source and optional verified-command context while leaving investigation and
editing to the agent. SWE-bench evaluates issue-to-patch behavior on real GitHub issues [2]. The present panel uses
author-designed extensions to public repositories. Its results describe an installed-system ablation within that panel;
they supply neither a SWE-bench score nor a direct performance comparison with these systems.


3    Architecture and evidence boundaries
Memglide prepares repository context and records the source and policy used to prepare it. Its central design choice
is conservative selection from current local files. Lexical evidence, static syntax and bounded dependency expansion
produce a small source bundle without an embedding model or auxiliary language-model request. The coding agent
interprets the task, edits the repository and checks its work. Memglide changes context preparation rather than model
weights.
    The implementation has two entry paths. Interactive clients reach a common service through a command-line
interface, loopback HTTP API or MCP STDIO server. The service combines repository indexing, context retrieval, a
SQLite database and explicit session memory; a dashboard uses the HTTP API. The native launcher, memglide-codex,
Memglide: Bounded Repository Context                                                                                   3


calls the source-preparation libraries directly before executing Codex. The experiment measures this prelaunch path,
shown in Figure 1. Interactive retrieval, the dashboard and session-memory reuse require separate evaluation.
  Repository registration resolves the Git root and records project state. The SQLite FTS5 index stores searchable
source, file hashes and metadata, symbol locations and signatures, and conservative dependency edges. Python structure
comes from the standard AST; JavaScript and TypeScript use an isolated Tree-sitter worker. Incremental refresh checks
current files before using indexed evidence. Dynamic imports, generated code and runtime dispatch can leave static
dependencies unresolved, limiting what the selected context represents.
  The interactive context engine combines identifier and path matches, normalized terms, FTS5 evidence and graph
expansion. Session memory stores caller-submitted observations, decisions, errors and fixes with provenance, timestamps
and source versions. Sessions have inactivity and absolute expiry limits. Returned context passports identify source
hashes, memory versions and omissions. These features provide versioned context within an active session; the
experiment does not measure cross-session reuse. The native prelaunch selector follows a separate deterministic
algorithm and does not automatically inject session observations.
  Prelaunch selection first checks whether preparation is enabled, context has already been supplied, and an approved
project and eligible task are available. Ineligible requests retain the exact original task. The v4 policy then securely
refreshes the index and screens production files. Known tests, examples and demonstration directories are excluded
from production competition. Potentially relevant unsupported files, partial indexing or an overfull candidate frontier
cause abstention. Coverage is therefore an observable policy outcome: reading source successfully does not establish
that the task received useful context.
  Remaining supported candidates are parsed into runtime or declaration syntax units. Normalized query terms receive
candidate-set frequency weights 𝑤 (𝑡) = log(1 + (𝑁 + 0.5)/(df (𝑡) + 0.5)). Here 𝑁 is the number of files passed to syntax
ranking, and df (𝑡) counts those files with term 𝑡 in the clean body or header of any eligible-role syntax unit. A file
counts once even if several units match; this frequency is computed on the bounded candidate set, rather than the entire
repository. A unit is sufficient if it has an explicit current anchor, or at least two distinct clean body/header matches
including one body match. Explicit and sufficient evidence receive large priority terms in ranking. The remaining score
combines body, header, path and documentation weights with coefficients 3, 2, 0.25 and 0.05. This score orders evidence;
it is not a calibrated confidence. An independently competitive file causes abstention unless the leader has the required
body-evidence dominance.
  After accepting an anchor, Memglide reads the complete file and at most three resolved direct production helpers.
It checks their current hashes and selection evidence before rendering the task. “Full source” refers to these selected
files, not repository-wide or transitive dependency coverage. Final handoff revalidates inspected competitors, selected
source, approval and ignore policy. A changed proof prevents reuse of the prepared context. Source, comments and
strings remain project data for the coding agent to interpret.
  Each phase has its own bounds. Default indexing permits 20,000 files and 100 MiB of eligible source, with a 512,000-
byte per-file read limit. The v4 task limit is 4,000 UTF-8 bytes and 64 normalized non-generic terms, each at most 128
characters. Coarse screening permits 100 files and 2 MiB; syntax analysis permits 24 files and a separate 2 MiB. The
syntax worker has a five-second timeout, 200,000-node limit and 1,000,000-byte output limit. Added context defaults
to 12,000 UTF-8 bytes, with an additional ceil(bytes/3) planning limit of 4,000. This proxy is not a provider token
measurement. Repeated freshness checks mean that phase byte limits are not whole-workflow I/O or memory bounds.
  The selected workflow adds public-command assistance through explicit verification. The caller declares atomic
argument lists and allowed environment updates. A verifier records a fresh bounded public-text tree, fingerprints
4                                                                                                       S. C. R. Kailasam


declared executable files, runs the checks, and records exit status, positive behavioral-test counts and log hashes. It
checks the tree, policy and tools again before writing a canonical receipt outside the project. The caller retains the
trusted receipt hash. Because public tests may execute repository code, verification is a separate authorized action;
context preparation does not itself run those commands.
    The launcher loads the pinned receipt, checks its current bindings, and places the declared commands and observed
baseline results beside the selected source. Allowed environment updates appear explicitly in the card. These results
concern the starting repository, before the feature is implemented. Stale, unavailable or oversized optional facts leave
ordinary source preparation available. An invalid explicitly pinned receipt on an active workflow path is an error. Before
native execution, the launcher repeats source selection and checks the exact rendered transformation. Abstention
preserves the task bytes.
    The trust boundary separates local preparation from an external coding model. Selected source is sent to Codex;
local-first describes where the index and state reside. Secure readers enforce containment, reject symlink traversal and
read bounded regular UTF-8 files. Known sensitive filenames and content patterns are filtered heuristically. Hashes
establish equality at checked reads, not semantic safety, permanent freshness or universal secret detection. A command
receipt covers eligible public text and declared executable bytes, not every transitive dependency, binary resource or
undeclared environment setting. Command-runner time and output limits also differ from operating-system isolation.
    These boundaries motivate separate evaluation of activation, functional success, preparation time, native execution
time and token-tariff equivalents. The source-and-command workflow incurs verification and freshness costs. Finite
public and hidden checks do not establish universal correctness, semantic quality of new tests or general coding
superiority. Natural abstentions and unknown telemetry remain in the record. In particular, the base58 oracle’s output-
bound checks cannot prove the requested allocation order. Launcher results do not establish benefits for unmeasured
memory, API or dashboard features.


4     Evaluation design
4.1    Tasks and prospective readiness
The panel contains one author-designed feature addition in each of twelve newly pinned public repositories: six Python
projects and six JavaScript/TypeScript projects. Two of the latter tasks require only JavaScript changes; four require
runtime and declaration changes. Four JavaScript/TypeScript roots share a maintainer. The projects are small and
purposively selected for executable upstream checks. They are not a sample of historical issues.
    Repository provenance, commit hashes, retained public inputs, prompts and commands are committed before native
outcomes. This local hash freeze is not a public preregistration. Screening records retain acquisition and compatibility
rejections, including an obsolete Python testing dependency and an incompatible upstream Node execution setup.
Repository novelty is relative to the earlier Memglide evaluation roots; the model’s training data are unknown.
    Tasks and checks were developed with AI assistance. Separate Codex agents proposed prompts and prepared feature
oracles, reference implementations and plausibly incorrect controls. Another agent reviewed task–oracle agreement
and control records. These are separate authoring roles, not independent human replication. Baseline, reference and
incorrect variants across twelve tasks provide thirty-six expected control outcomes, with positive original public-test
counts: the baseline fails the feature, the reference passes, and the incorrect implementation can fail without changing
upstream tests. These controls do not establish exhaustive coverage. Original tests, configurations and provenance are
retained; public declaration compilation is enforced where applicable. Regression tests are requested, but their presence

4.2   Conditions, allocation and execution
Arm A runs the installed launcher in explicit off/pass-through mode. Arm B enables v4 discovery and compact source
context. Arm C uses the same source policy plus the selected verified public-command card. C versus A measures the
6                                                                                                           S. C. R. Kailasam


overall installed intervention; C versus B compares the added card and fresh-verification workflow. Abstention remains
a policy outcome, and its indexing and verification overhead belongs to the assigned workflow.
    Each task receives all three arms twice: seventy-two scheduled workflows and twenty-four cells per arm. Before
outcomes, seed 20261027 shuffles the task sequence and a multiset containing each of the six arm orders twice. Repeat
two reverses the entire first-repeat task/arm sequence. Assignments run sequentially, each with a fresh project copy,
native state and thread. The model alias is gpt-6.1-sol, with low effort and the default service tier, using Codex CLI 0.159.2.
Each launcher receives the same feature-request stdin and developer instructions. Native prompts differ by assigned
context; response schema, tools and network-disabled workspace-write configuration are shared. Project-document
injection is disabled identically. Thirty-six installed zero-model handoffs establish expected treatment before sealing.
Actual prompt bytes and arguments are captured during native execution and checked against that commitment.
    Session counts refer to the coding-agent codex exec evaluation path. Authoring controls, handoff checks and
public/private graders can use local codex sandbox processes without making model requests; these processes are not
additional coding-model sessions. Neither CLI process counts nor observed agent commands reveal internal provider
inference counts.
    Each assignment is allocated durably once. There are no retries, replacements or outcome-driven repeats, and the
controller admits only the next unused assignment. Missing whole-attempt usage, lifecycle failure or integrity failure
causes a durable stop; unrun cells remain unavailable. The maximum is seventy-two scheduled native dispatches. A soft
USD 18 allowance uses the uniform accounting convention, with a USD 0.25 reserve before another call is admitted. It
bounds neither account charges nor the cost of an admitted call.


4.3   Timing, isolation and grading
Public-source copying and Git-baseline construction occur outside every workflow timer. Timing starts before arm-
specific registration, indexing or verification and ends after native process-group cleanup. C includes public baseline
verification and removal of its newly generated logs, build outputs and caches. Original source and Git bytes, and the
provider manifest, are checked afterward. This cleanup is an experimental control, not automatic shipping behavior.
Component measurements separate indexing, verification, cleanup, launcher preparation and native execution. An
absolute ninety-second setup allowance covers setup through launcher preparation. Native execution receives a separate
three-hundred-second allowance from the recorded local bridge handoff. Native wall time includes final local exec
setup and cleanup; it does not isolate remote inference latency. Grading and evidence packaging are excluded.
    All arms use a frozen environment profile, including TERM=xterm and disabled supported runtime caches. Projects
and run caches are fresh. Operating-system page caches and provider prefix caches are uncontrolled; observed cached
input is reported. No unrelated heavy validation runs during measured execution.
    Before launch, private grader/reference/control bundles and revealing logs are encrypted and authenticated with
AES-GCM. A random 256-bit key remains only in the external orchestrator store. Ciphertext and hash commitments
may remain locally, but every private plaintext root is absent before dispatch. This sequesters the new oracle plaintext;
it is not an operating-system isolation claim. Exact committed bytes are restored after native closure or a durable stop.
    Private and public grading then runs with candidate source read-only, network disabled and only grader artifacts
writable. Inherited global temporary write roots are disabled. Source and protection hashes are checked before and
after grading. Strict success requires valid native completion and usage, treatment fidelity, intact protected inputs, valid
grading infrastructure, and passing committed feature and original public checks.

4.4    Accounting and statistical analysis
The two primary contrasts are C minus A and C minus B in uniform API-equivalent dollars. Repeated costs are averaged
within each task before computing its paired arm difference. The fixed convention is [(input minus cached input) × 5 +
cached input × 0.20 + output × 15] / 1,000,000. This historical tariff convention is neither an invoice nor a current-price
claim. Ordinary coding failures retain observed costs; unknown usage is never replaced with zero. A complete-panel
estimate requires all twelve task clusters and both repeats for the contrasted arms. Otherwise the primary total, effect
and test are unavailable, and known subtotals and missing identifiers are reported. Actual billing and internal provider
request counts are unavailable.
    Complete contrasts receive pointwise 95% paired task-bootstrap intervals from 10,000 resamples, using seed 20261029.
Resampling retains both repeats and paired arms. For exact tests, conditioning on the third arm’s first-repeat position
creates three strata of four tasks, each containing two relative orders of the compared arms. Enumerating choose(4,2)ˆ3 =
216 legal allocations, with joint repeat-label swaps, respects the balanced design. Two-sided tests count ties and require a
pairwise sharp null and no cross-arm/provider-cache carryover. Holm adjustment covers the two predeclared cost tests;
missingness does not reduce the family. Native-price/cache-write sensitivities, tokens, workflow components, readiness
strata and joint-success timing are secondary descriptive analyses. Command-text read/test counts are heuristic.
Cheaper failures cannot establish efficiency, and matching observed success counts does not establish population quality
equivalence.
    The study is precision limited. Planning from seven earlier complete two-repeat task clusters gives an unstable
cost-difference standard deviation of USD 0.03441. An optimistic normal approximation suggests a detectable difference
near USD 0.03063, about 25% of the earlier A mean, for twelve clusters at 80% power and first-step two-sided alpha
0.025. This is not achieved power or a guarantee for the exact test. Earlier adaptive prototype results remain exploratory
and are not pooled with the installed-system panel.



5     Development history
The final configuration emerged through unsuccessful and partly successful evaluations. The supplement inventories
23 historical stages and their reports. Some rows reanalyze earlier attempts and must not be counted as new model
sessions. The stages explain the implementation and measurement choices; their different conditions and task sets do
not form a common representative benchmark.
    Early native MCP experiments showed that retrieval could be costly. In one matched cohort, the context-assisted
condition used 2.751 times the input tokens and 1.465 times the Codex-plus-index time. An optimized cohort still
increased input by 32.82% and Codex-plus-index time by 17.88%, although both conditions passed their finite checks.
Known-path source preloading later reduced some aggregate measures, without establishing automatic discovery or a
joint cost and speed improvement. A partial memory study also failed to establish a warm-memory benefit.
    Source delivery needed its own verification. Earlier automatic policies often abstained or selected an incorrect target
in local tests. In a fresh v4 native comparison, the automatic condition added source on none of its 24 assignments,
leaving task prompts identical to the pass-through baseline. Agent differences in that cohort cannot establish a source-
preloading effect. A subsequent active pilot delivered source, but one failure changed a lower observed cost per attempt
into a higher cost per strict success. A feedback-informed repair was retained as development evidence, without
replacing the original attempt.

6   Results
All 72 scheduled assignments completed with valid native telemetry and complete whole-attempt usage. Each arm passed
24 of 24 strict assessments. There were no unavailable outcomes, protected-file violations or grading-infrastructure
failures. Before candidate grading, all 36 author controls were rechecked through the final frozen sandbox: references
passed the feature checks, baselines and deliberately incorrect variants failed them, and original public checks passed
throughout. These outcomes show that all submitted patches passed the committed rubric on this panel; the saturated
scores cannot establish population quality equivalence or distinguish the arms’ general coding ability.

7     Interpretation and limitations
The experiment measures a context-preparation policy around one installed coding-agent configuration. Source hashes
identify supplied bytes; command receipts describe checks on the starting repository; finite grades assess specified
behavior; native counters support tariff calculations. None alone establishes better coding in general.
     Coverage limits the intervention. Seven of twelve tasks preload at readiness and five abstain. Runtime and declaration
files can compete, and source-role classification remains heuristic. The primary intention-to-treat comparison retains

8    Conclusion
Memglide implements bounded source discovery and optional verified public-command context around an existing
coding agent. The installed-system comparison completed all 72 assignments with known usage and passing finite
functional, public and integrity checks. Source was supplied on seven of twelve tasks; the policy abstained on five.
     The source-and-command workflow had a 13.69% lower observed uniform cost than pass-through and a 10.04%
lower cost than source alone. Neither prespecified familywise test established a reduction, and workflow timing did
not establish a speed advantage. Fresh verification partly offset the shorter observed native execution. These results
support reporting a functioning, auditable implementation and a measured cost estimate with uncertainty. Broader
claims require a larger, independently designed task panel and additional models. Coordinated runtime/declaration
selection, verification deferred until source eligibility, and amortized receipt reuse are concrete directions for a new
evaluation; none is credited with an unmeasured benefit here.
